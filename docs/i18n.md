# Internationalisation (i18n)

SWB Auto PDF Invoices ships in 19 languages. Everything a merchant or their
customer can read — admin screens, PDF invoices, packing slips, emails, toasts,
validation errors and the order-details extension — comes from
`/locales/<code>/common.json`.

---

## 1. Folder structure

```
locales/
  en/common.json          ← source of truth; every other locale mirrors its keys
  de/common.json
  fr/common.json
  … 19 locales total

invoice/
  i18n.php                ← the whole i18n core (loader, t(), detection, Intl)
  sql/2026_08_03_add_app_locale.sql

css/
  rtl.css                 ← loaded only for Arabic/Hebrew

js/
  script.js               ← reads window.SAPI_I18N injected by footer.php

tools/
  check-translations.php  ← key parity / placeholder / JSON validator

shopify-admin-extension/
  src/i18n.js             ← translator for the admin action
  src/locales/*.json      ← generated; do not edit by hand
  scripts/sync-locales.js ← copies extension.* keys out of /locales
```

## 2. Required packages

**None for the PHP app.** The core is ~30 KB of plain PHP with no Composer
dependency, so `composer.json` is untouched.

It uses PHP's **`ext-intl`** for locale-aware dates, numbers and currency.
Every formatter checks for it and degrades to `number_format()`/`date()` if it
is missing, so the app still runs without it — dates and money just look less
idiomatic. To confirm it is enabled:

```bash
php -m | grep intl
```

If it is missing: `sudo apt install php8.3-intl` (Debian/Ubuntu) or enable
`extension=intl` in `php.ini`, then restart PHP-FPM/Apache.

The extension bundle needs no new npm packages either — `sync-locales.js` uses
only Node built-ins.

## 3. Installation

```bash
# 1. Run the migration (adds stores.app_locale)
mysql -u USER -p DBNAME < invoice/sql/2026_08_03_add_app_locale.sql

# 2. Verify the catalogs are healthy
php tools/check-translations.php

# 3. Rebuild the admin extension so it picks up its catalogs
cd shopify-admin-extension && npm run build
```

The migration is additive and nullable — deploying the code *before* running it
is safe. `i18n_storage_ready()` probes for the column and the language switcher
simply declines to save until it exists.

## 4. Language detection

Resolved once per request by `i18n_boot($store)`, in this order:

| # | Source | Where it comes from |
|---|--------|---------------------|
| 1 | `stores.app_locale` | the merchant picked it in Settings → Language |
| 2 | `stores.primary_locale` | Shopify shop locale, captured at install |
| 3 | `Accept-Language` | browser, q-weights honoured |
| 4 | `en` | fallback |

Tags are normalised, so `de-DE` → `de`, `pt-BR` → `pt`, `zh-Hans` → `zh-CN`,
`zh-HK` → `zh-TW`, `no`/`nn` → `nb`, and legacy `iw` → `he`.

Customer-facing output (invoice PDFs, packing slips, invoice emails) re-boots
with the **store's** locale, so a merchant browsing in English still sends
German invoices from a German shop.

## 5. Using it in code

```php
require_once 'i18n.php';
i18n_boot($store);              // once, after $store is loaded

echo e('settings.title');                              // escaped — use in markup
echo e('common.selected_count', ['count' => 3]);        // with interpolation
echo t('toast.email_sent');                             // raw (JSON, headers, mail)
echo t_html('help.free_3');                             // translation may contain markup
echo t_status($invoice['invoice_status']);              // DB status → label

echo fmt_currency(1234.5, 'EUR');   // de: 1.234,50 €   en: €1,234.50
echo fmt_date($row['created_at']);  // de: 04.08.2026    en: Aug 4, 2026
echo fmt_number(1234567);
echo fmt_percent(18);
```

**Which function?**

| Function | Escapes translation | Escapes params | Use for |
|---|---|---|---|
| `e()` | yes | yes | anything inside HTML — the default |
| `t()` | no | no | JSON responses, email subjects, `die()` |
| `t_html()` | no | yes | translations that intentionally contain tags |

A missing key returns the key itself (`settings.title`), so gaps are visible and
greppable rather than blank.

## 6. Adding a language

1. Copy `locales/en/common.json` to `locales/<code>/common.json` and translate.
2. Add one row to `i18n_locales()` in `invoice/i18n.php`:
   ```php
   'tr' => ['label' => 'Türkçe', 'dir' => 'ltr', 'intl' => 'tr_TR'],
   ```
3. Add the code to `LOCALES` in `shopify-admin-extension/scripts/sync-locales.js`
   and add the matching `import` + `CATALOGS` entry in `src/i18n.js`.
4. `php tools/check-translations.php` — must report `ok`.
5. `cd shopify-admin-extension && npm run build`.

Nothing else changes: the switcher, `<html lang dir>`, RTL loading and the PDF
templates are all driven off that one table row. An RTL language needs
`'dir' => 'rtl'` and no CSS work — `css/rtl.css` keys off `[dir="rtl"]`.

## 7. Adding or changing a string

1. Add the key to `locales/en/common.json` (flat, dot-notation, grouped by
   screen: `settings.*`, `invoice.*`, `toast.*`).
2. Use it in code via `e()` / `t()`.
3. Add the same key to the other 18 files — or ship English-only and let the
   fallback cover it until translations land.
4. `php tools/check-translations.php` before committing.

**Rules that keep this maintainable**

- **Translate whole sentences, never fragments.** Word order differs between
  languages; `"You have used all " . $n . " invoices"` cannot be translated
  correctly, `limits.orders_reached` can.
- **Never concatenate a translated string with a number or name** — use a
  `{{placeholder}}`.
- **Keep placeholder names identical across locales.** The checker enforces this.
- **Don't reuse a key across contexts** just because English matches. `nav.packing_slips`,
  `bulk.tab_packing_slips` and `packing.title` are all "Packing Slips" in English
  and legitimately diverge elsewhere.
- **Email subject/body use single braces** (`{invoice_number}`) because merchants
  edit them by hand; everything else uses i18next `{{var}}`. The two never collide.

## 8. Missing translations

At runtime a missing key falls back English → the key itself, and is recorded.
To surface them while developing, define in `config/config.php`:

```php
define('I18N_DEBUG', true);
```

Every unresolved key is then written to the PHP error log as
`[i18n] MISSING KEY "settings.foo" (locale: de)`. In production the constant
stays undefined and nothing is logged, but `i18n_missing_keys()` still returns
the set for the current request if you want to expose it on a debug page.

## 9. Performance

Only the active locale is read from disk, plus English when a key is missing —
so 19 languages cost the same as 1. Catalogs are memoised per request, and the
browser receives only the ~50 keys `script.js` actually uses (see
`i18n_js_keys()`), not the full 384-key catalog. `css/rtl.css` is requested only
by Arabic and Hebrew merchants.

## 10. Future React / i18next port

The JSON is deliberately i18next-shaped: flat keys, `{{var}}` interpolation,
one namespace per file. A React port reuses `/locales` verbatim:

```js
i18n.use(initReactI18next).init({
  fallbackLng: 'en',
  keySeparator: false,        // keys contain literal dots
  ns: ['common'],
  backend: { loadPath: '/locales/{{lng}}/{{ns}}.json' },
});
```

Keep `i18n_normalize_locale()` (PHP) and `normalizeLocale()` (extension) in step
when the locale list changes — they implement the same mapping.
